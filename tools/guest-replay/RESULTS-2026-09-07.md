# Initial local Firefox checks

These are diagnostic trials, not a statistically controlled throughput study.
The server/build ran on kreijstalnuc; execution ran in a separate, visible local
Firefox profile on the throttled target computer. The user's original Firefox
session was not reloaded. No production runtime setting was changed by the lab.

## Audio fixture v2

One active 256-frame stereo mixer call at 22050 Hz, SHA-256:
`09336cb68dc07f9ed4d40ce25a90a1e2eecbe962d664aa040fa8072e2f1caa3a`.
Its playback budget is 11.61 ms. All trial outputs and captured receiver state
matched the oracle exactly.

| Backend | First execution (ms) | Subsequent executions (ms) |
| --- | ---: | --- |
| JavaScript | 154 | 10, 6, 6, 6 |
| Wasm + interpreter fallback | 48 | 14, 12 |
| Interpreter | 334 | 290, 282 |

The Wasm arm executed 29 Wasm entries each trial; the JavaScript arm executed
none. Preparation, graph reset (~520–575 ms) and exact verification (~720–930 ms)
were excluded from these execution times. Browser timing resolution was about
1 ms. Different backends were tested sequentially; GC and engine warming are
not controlled. A single repeated block does not represent all voice states.

This shows substantial headroom relative to interpretation for this audio job,
but does not establish stutter-free music. Cold executions missed the deadline
even with runtime code preparation complete. Browser-engine cold-code work
still needs to be addressed under the before-main preparation contract, without
moving observable guest execution before main.

## Rejected visual fixture v2

The first captured mesh call left the entire raster black. Its argument/state
checks passed, but that is not a useful oracle for visible drawing. Do not use
its 2–22 ms warmed JavaScript timings to claim rendering performance. Its Wasm
arm also showed heavy fallback (around 28,390 interpreter ticks and only 2 Wasm
entries in later trials), which remains a path worth investigating.

Source inspection showed that `p.a` prepares geometry; the caller subsequently
invokes `hi.a` to rasterize it. The recorder now captures that rasterizer and
requires changed, non-black pixels. Earlier combined-budget rows using v2 visual
data are not evidence for full-frame or full-game 24 FPS.

## Accepted visual fixture v5

`hi.a(IIIIILnf;II)V`, SHA-256:
`fccc11ddd2446c297d3271e93a6be9f948dc1a69f15f626ebeb570e19df93363`.
This changes 1,141 pixels in a 540 x 140 buffer (nine colors). It is one small
visible piece of the logo, **not the whole logo/frame**, and excludes the
preceding geometry preparation. The required guest texture-descriptor table is
included. All nine local Firefox trials matched the entire captured pixel buffer
and argument graph exactly; all reported `timedCompiles: 0`.

| Backend | First execution (ms) | Subsequent executions (ms) |
| --- | ---: | --- |
| JavaScript | 146 | 49, 23 |
| Wasm + interpreter fallback | 141 | 105, 114 |
| Interpreter | 3669 | 3583, 3551 |

Preparation took 9.48 s (JS), 8.74 s (Wasm), and 7.13 s (interpreter metadata).
The prepared call closure contains 15 methods. Wasm executed 121 entries per
trial, alongside ~8,976 scheduler ticks; interpreter took ~467,097 ticks.

The useful next experiment is to instrument which rasterizer callees fall back
and how often, then compare a prepared direct-call implementation using this
unchanged oracle. These measurements establish an execution-path cost gap, not
the exact split between dispatch, fallback, arithmetic, and memory overhead.
Neither these trials nor the audio block prove 24 FPS feasible or impossible.

## Final combined JavaScript check

Audio v2 + accepted visual v5, five trials; visual JS was already prepared and
had executed three earlier trials, audio JS was newly prepared. All ten output
checks passed, with zero reported timed compilations.

| Trial | Audio execution (ms) | One mesh rasterization (ms) |
| --- | ---: | ---: |
| 0 | 157 | 43 |
| 1 | 9 | 20 |
| 2 | 10 | 16 |
| 3 | 5 | 13 |
| 4 | 4 | 12 |

The last trial's isolated-demand estimate is about 63% of one thread, assuming
this same audio block at its playback cadence and this same draw 24 times/sec.
That deliberately omits all other game work, geometry preparation, full-frame
drawing, presentation, live scheduling, and the diagnostic reset/verification
cost. It is not a measured frame rate or proof that 24 FPS is attainable.
