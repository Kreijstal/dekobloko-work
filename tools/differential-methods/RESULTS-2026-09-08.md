# First differential actual-method measurements

All three drivers execute identical JARs on local HotSpot and local stock
Firefox. These are **preliminary measurements: three HotSpot forks, one valid
Firefox fork per workload**. No repeatable reduction win or compiler fix is
claimed. Each fork has one first-call sample, twelve untimed warmup calls,
and eight post-warmup samples. "Warm" below is their median, not a claim of
steady-state tier convergence.

| Operation | HotSpot cold / warm (ms) | Firefox cold / warm (ms) | Cold excess |
| --- | --- | --- | --- |
| Actual Candy foreground decode + palette expansion | 169.977 / 4.744 | 768 / 137 | 598.023 ms |
| Actual sample, one stereo voice, 256 frames | 0.0845 / 0.0285 | 79 / unresolved below ~1 ms | 78.916 ms |
| Actual Candy foreground zero-angle transform | 37.197 / 1.800 | 41 / 9.5 | 3.803 ms |

Ordering uses elapsed cost, not ratios. The audio ratio would be spectacular
but misleading as a prioritization argument without considering its absolute
cost, first-use state, and actual game frequency. Its warmed samples round to
zero at the accepted browser guest clock's resolution, so no warmed speedup or
ratio is reported. No FPS forecast follows from these measurements.

## Correctness and executed work

- Decode: `hf.a(Z[B)V → sc.a(B)Ldm;`, real archive 1/group 7/file 1,
  `sweets/sweets_foreground`, 213,287 input bytes. All nine checksums per fork
  equal **1204680094**. Independent JS decoding gives 461×461 pixels; the
  Firefox final output matches all **212,521 pixels byte-for-byte**, SHA-256
  `fa1aa21771db90e087b5e92667fc0c589e768a5e8c004f54a99b25251bb86c00`.
- Rendering: `dm.b(IIIIII)V`, the transform entry called from `gh` for
  `ec.field_c`. Unity scale, zero angle, actual Candy sprite and dimensions.
  All checksums match the independent pixel oracle. The selected Wasm state
  reports **21 runs, zero exits, zero fuel exits**. This angle is not a claim
  to cover all rendering cases.
- Audio: `kl.a([III)V`, one voice, actual Vorbis setup/sample from archive 3,
  group 0, files 0/1. Real decoding is outside the production timer; private
  decoder construction uses reflection only during fixture setup. All checksums
  equal **62529537**, matching a HotSpot `-Xint` control. Java verification
  explicitly rejects silence. No device/backend, queue, polyphony, or underrun
  result is implied.

The decoder's generated metadata names structured-SSA bodies. Its selected
Wasm states show zero runs, unlike the rendering entry. This is path evidence,
not exclusive time attribution or proof of why the decoder is slow.

## Connection to the transition—and missing evidence

The source path is `Geoblox.p(7) → ug.a → qc.a → mf.a → hf.a`, followed by
`sc.a`, for the actual Candy foreground. This establishes a bounded operation
from Candy resource loading. It does **not** establish how much of the real
Solar → Candy gap it occupies: `p` may also be called by background update
work before the visible transition. A bounded real transition trace and
matching runtime-path signature remain necessary before claiming a freeze
reproducer or transferring an optimization.
