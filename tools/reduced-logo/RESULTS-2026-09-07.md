## Animated Jagex logo — measured, not loading/menu

The matching-build animation counter identifies a **10.805 s** interval:
**25 presentations, 2.3137 FPS**. Frame-gap median **352 ms**, p95 **672 ms**,
p99/max **1,243 ms**. Worst rolling one-second window: **zero frames**.
All 24 complete inter-presentation gaps exceed the 41.67 ms target.
Preparation, the earlier one-off logo preprocessing render, loading panel,
and menu are excluded. The animation's fade-in/out remain included.

This run had no sampling profiler. The presentation/tick probes and nine
external screenshots remained active; their overhead is not claimed to be zero.
The screenshots verify the animated geometry itself, not the static Jagex
badge on the loading panel. `results/game-logo-visible.png` is one example.
Raw data: `results/game-logo-unprofiled.json`; full screenshot sequence is in
`/home/kreijstal/work/deko-firefox/logo-unprofiled/`.

A separate sampling-profiler run measured 25 presentations in 12.361 s
(2.0225 FPS). Its samples were restricted to the counter-defined logo interval.
Of 6,066 samples, 4,592 had a nearest generated frame: 2,241 baseline,
2,151 Ion, 154 baseline-interpreter and 46 unknown. The largest individual
nearest-generated category was the wide triangle routine
`wh.a(IIIIIIIIIII[IIIIII)V`: 666 baseline samples. Mesh routine `hi.a`,
triangle setup `nb.a` and span routine `jf.a` also appear prominently.
These are sample attributions, not additive exclusive CPU times or a proven
explanation of all stalls. Summaries are retained in `results/`; full raw
profile is `/tmp/actual-logo-profile.json` and filtered profile
`/tmp/actual-logo-only-profile.json` (also archived outside the repo).

## New Java reduction: useful negative result

Twelve procedural boxes, 540x140 raster, 32 fixed frames. No game coordinates,
assets, serialized state, audio mixer or guest warmup. Wide triangle setup,
clipping, fixed-point colour interpolation and alpha spans model the observed
rendering call structure. A/B differs in a separate static span call versus
inline span arithmetic. Work volume was not adjusted to force 2 FPS.

| Class compiler / arm | Compute + publication FPS | First frame | Median | Maximum |
| --- | ---: | ---: | ---: | ---: |
| javac / separate span | 42.16 | 113 ms | 16 ms | 113 ms |
| javac / inline span | 33.79 | 157 ms | 17 ms | 165 ms |
| javac.js / separate span | 35.32 | 122 ms | 17 ms | 122 ms |
| javac.js / inline span | 28.50 | 151 ms | 20 ms | 151 ms |

All four runs have checksum **-299842540**, 32 presentations and zero post-main
JVM compilations. These are individual cold runs, not statistically established
comparative speedups. They do not reproduce the game's sustained 2.31 FPS.
Cold spikes are reproduced, but that is a narrower finding.

Same-machine HotSpot checked every pixel after every frame in both arms and
matched the expected checksum, for both class compilers. An idle-browser
repeat took 117/145 ms total for all 32 kernel frames with javac output,
119/147 ms with javac.js output. HotSpot excludes AWT publication, so those
totals are not end-to-end browser FPS comparisons. An earlier run overlapped
preparation and is not used for these totals.

Conclusion: the logo failure is now measured. Ordinary wide calls and clipped
scanlines alone are insufficient to reproduce it. The large generated
control-flow/restoration paths seen in the actual profile remain candidates;
this experiment does not yet isolate their causal contribution. No runtime
fix or full-game acceptance is claimed.
