# Deterministic readable GeoBlox sources

Generate a separate readable Java tree from an exact, compilable source corpus.
Names come from reviewed rules keyed by JVM identities, not a global text
replacement or a fresh guess on every run. The first GeoBlox rules cover confirmed
sprite/raster state, nearest and smooth rotation, bilinear sampling, music decoding
and audio roles. This is an incremental naming refactor; it does not simplify
control flow or infer names for all unknown locals and classes.

The generator is `scripts/readable-java.mjs`; the current reviewed game rules are
`apps/launcher/readability-rules/geoblox-v3.json`. Historical v1/v2 rules remain
available; each revision records the preceding rules hash and includes all earlier
names. The pinned corpus has 303
files and source-tree SHA-256
`45b38190d2b94f1daa68bdf4ea16aa516be2feda493dceabe51ef8146cce6d7f`.
That digest identifies the actual source bytes, independently of a preparation
profile or Git metadata. The corpus exactly matches `games/geoblox` in
`Kreijstal/funorb-decompiled` at commit
`3230e3092c687d210ba068bdfd7667a5213d22fb`; the source repository, commit and
subdirectory are recorded in the rules and output provenance. Both the clean
sibling checkout and `.work/slow-host/noaudio/src-base` match this digest. The
audio experiment's `src-noaudio` tree differs and is refused by these rules.

Run from Deko with Node.js supporting `fs.cpSync` and a JDK providing javac:

```sh
git clone --no-checkout https://github.com/Kreijstal/funorb-decompiled.git .work/funorb-readable-input
git -C .work/funorb-readable-input checkout --detach 3230e3092c687d210ba068bdfd7667a5213d22fb

node scripts/readable-java.mjs \
  .work/funorb-readable-input/games/geoblox .work/geoblox-readable-v3 \
  apps/launcher/readability-rules/geoblox-v3.json lib/dekobloko-stubs.jar

# Re-analyze, regenerate and compare all generated bytes without overwriting:
node scripts/readable-java.mjs \
  .work/funorb-readable-input/games/geoblox .work/geoblox-readable-v3 \
  apps/launcher/readability-rules/geoblox-v3.json lib/dekobloko-stubs.jar --check

node --test scripts/test-readable-java.mjs
```

`INPUT OUTPUT RULES_JSON [CLASSPATH] [--check]` is the complete CLI. `JAVA` and
`JAVAC` select executables when the default PATH tools are unsuitable. Source
analysis and compilation use `--release 8`, UTF-8 and disabled annotation
processing. Classpath entries must be regular files; their names and content
hashes are recorded. Input/output trees must be separate. Generation refuses
existing output; choose a new directory for changed rules or use `--check` to
verify the existing one. Sources are emitted only after validation succeeds.

## Rule identities and naming convention

| Kind | Example identity | Readable name |
| --- | --- | --- |
| Class | `C:dm` | `Sprite_dm` |
| Field | `F:vb.field_c:[I` | `framebuffer_field_c` |
| Exact method overload | `M:dm.b(IIIIII)V` | `rotateNearest_b` |
| Parameter | `P:dm.b(IIIIII)V#4` | `angle_param4` |
| Local declaration | `L:dm.b(IIIIII)V#9`, original name `var7` | `angleRadians_var7` |

Class names use Java binary names. Field/method types use JVM descriptors.
Parameter indexes are zero-based positions in the declaration, not JVM local
slots; a `long` or `double` is still one parameter. `L:` identities identify
locals by enclosing method and zero-based declaration ordinal, excluding formal
method parameters. Initializer locals use a distinct `<initializer>` context.
Local rules require `originalName` in addition to that identity, so a rule cannot
silently rename a different declaration with the same ordinal. Identically named
locals in separate blocks and catch scopes remain distinct symbols.

```json
{
  "symbol": "L:dm.b(IIIIII)V#9",
  "originalName": "var7",
  "to": "angleRadians_var7",
  "evidence": "Masked 16-bit angle multiplied by 2*pi/65536 before sin/cos."
}
```

Every rule contains its original symbol, replacement name and evidence. Keep
the original spelling as a suffix. Use a semantic role only when source expressions,
tests or captured execution support it; leave uncertain symbols unchanged.
For example, `MusicDecodeStage_u` deliberately does not assert a particular
transform algorithm. The `SpriteState_wh` class also owns unrelated static helpers;
its name describes its instance data, not every method in that class.

Methods are descriptor-specific: the two `ua.b` overloads become `readBit_b`
and `readBits_b`. Virtual families must be renamed together. The initial nearest
rotation rule therefore includes both `dm.b(IIIIII)V` and its `il` override.
Platform callbacks cannot be renamed independently of their external contracts.
Constructors follow their class name automatically; constructors and class
initializers cannot be direct method rules. The generator also excludes
constructor-parameter rules and nested/local class rename rules.

## Second naming pass

V2 has **174 rules**, adding 128 to the original 46, including 82 guarded locals.
It names nearest/smooth rotation angles, forward/inverse coefficients, transformed
corners, clipping bounds, source coordinates and scanline counters. The decoder
now names its bit input, byte/bit cursors, packet cursor, PCM output and write
position, bit-reader accumulators and overlap-add buffers. GeoBlox's main class
now names archive polling, asset preparation, screen initialization, theme loaders
and the applet loop's initialization/update/render/audio/cleanup hooks. Those
hooks rename both `ch` declarations and `Geoblox` implementations.

Reused locals receive names describing both phases. For example,
`rightThenNegativeWidth_var20` starts as a right bound and later becomes a
negative width; `chunkBitsThenMask_var3` starts as a bit count and later becomes
a mask. Names do not imply an invariant the original code does not maintain.
All original arithmetic, pivot decrements, labels and control flow remain intact.

An actual generated decoder excerpt is:

```java
final static int readBit_b() {
    int bitValue_var0 = bitstreamBytes_field_L[byteCursor_field_y] >> bitCursor_field_j & 1;
    bitCursor_field_j = bitCursor_field_j + 1;
    byteCursor_field_y = byteCursor_field_y + (bitCursor_field_j >> 3);
    bitCursor_field_j = bitCursor_field_j & 7;
    return bitValue_var0;
}
```

The complete second-pass tree compiles with 5,062 identifier edits and preserves
all 167,702 recorded bindings and 388 override edges. Its source-tree output hash
is `58f507ce4101fc9f8bc31d5e544bdae0314046eb4841905afb5e05bcb8f8ba23`.
This records static verification and deterministic output, not whole-game runtime
equivalence or a performance result.

## Screen and gameplay naming pass

V3 has **288 rules**, adding 114 names to v2. The nine `c` instances are now
`GameScreen_c`, their shared menu/input base is `MenuScreen_ka`, and the `gh`
instance used during play is `GameplaySession_gh`. The original class suffixes
and JVM identities remain available in the generated mapping.

The main loop's state is named separately from the decompiler's control-flow
scaffolding:

| Original symbol | V3 role |
| --- | --- |
| `og.field_q` | `screens_field_q`, the nine screen controllers |
| `tc.field_c` | `currentScreenId_field_c`, committed screen |
| `ai.field_p` | `requestedScreenId_field_p`, transition destination |
| `nf.field_A` | `screenTransitionTick_field_A`, progress committed at tick 160 |
| `pg.field_e` | `screenChangePending_field_e`, consumed screen-change request |
| `el.field_o` | `gameplaySession_field_o`, active gameplay session |
| `el.field_i` | `gameplayReturnScreenId_field_i`, stored return destination |
| `cd.field_j` | `gameplayOriginScreenId_field_j`, originating menu screen |
| `t.field_i` | `menuActionIds_field_i`, screen/item-to-action lookup |

When current/requested IDs differ, the loop calls `updateTransition_c` on the
outgoing/incoming screens and advances the transition tick. At tick 160 it
commits the requested ID and resets the counter. Otherwise a nonnegative ID
calls `updateScreen_h`; `-1` delegates to `GameplaySession_gh.updateSession_a`
unless the existing special preparation branch is active. Rendering uses
`renderScreen_a` or `renderSession_a`, with a clipped split and named curtain
sprite while transitioning. Numeric screen/action IDs and special sentinels
remain unchanged; this pass does not invent a full enum from partial evidence.

The menu path now reads through `updatePointer_a`, `hitTestMenuItem_a`,
`handleMenuPointer_a`, `handleMenuKey_a`, `decreaseMenuValue_a`,
`increaseMenuValue_a`, `activateMenuItem_b`, and `renderMenuItem_a`. Selection,
hit bounds, row count/spacing, action identifiers, coordinates and parameters
are named. Every overridden menu method has matching names on both the base
and concrete declaration. Screen animation/active ticks, theme index and volume
preview state also have confirmed roles.

A generated activation excerpt illustrates the menu-to-gameplay boundary:

```java
el.gameplaySession_field_o = new GameplaySession_gh(this.gameApplet_field_p, var3_int != 0);
le.a((byte) -39);
ai.requestedScreenId_field_p = -1;
```

Gameplay now names its update/render methods, board angle, score/text,
points-popup accumulation/emission, score submission and session-exit screen
selection. Unknown mode flags, action constants and decompiler `statePc`
variables remain unchanged. Decompiled labels and large methods still limit
readability; naming these entry points does not simplify their control flow.

The full v3 tree compiles with 6,367 identifier edits, all 167,702 recorded
bindings and 388 override edges preserved. Its source-tree hash is
`7be948e39b0532ffd15064b602f61c6ca0e36b51997958d0423c06832899d227`.

## What is checked

The Java helper uses the JDK compiler's public Trees/Elements APIs to resolve
declarations and references across the complete input. It records original
tokens and source positions, then the Node driver changes only those token ranges.
Formatting, comments, literal strings and line breaks are retained. Unicode
escapes in identifiers/comments are refused rather than handled with an incorrect
untranslated lexer; normal literal escapes are left alone.

The tool compiles the original tree, checks rule presence and complete override
families, rewrites to temporary sources and compiles those sources too. It then
compares every recorded declaration/reference with the expected renamed identity,
including symbols that had no rename rule. This catches a rewrite that compiles
but binds to a shadowing local or a different overload. It also compares override
relationships after rewriting to reject newly introduced virtual dispatch edges.
Compilation failures, changed bindings, missing rules, duplicate rules or output
filename collisions prevent publishing the generated tree.

Focused fixtures execute both original and renamed code and compare results;
they cover overloads, inherited dispatch, shadowed fields, constructors with
arguments/locals, static/instance initializers, method references and untouched
comments/literals. Additional fixtures check stale input, overwrite refusal,
incomplete families, external callbacks, silent rebinding and new overrides.
Local-rule fixtures execute both versions, distinguish same-spelled locals in
separate scopes, retain catch bindings and reject missing/wrong original-name guards.

## Traceability and reproduction

The output contains:

- `src/`: all Java files, with class filenames renamed consistently.
- `SYMBOLS.md`: the explicit rule table and evidence for browsing.
- `mapping.json`: original and renamed declaration identities, including
  descriptor/owner changes induced by class rules; per-file input/output hashes;
  and every edit's original UTF-16 offsets, original token and replacement.
- `provenance.json`: source-tree, rules, generator and output-tree hashes,
  JDK identity, classpath hashes and validation results.

There are no timestamps, random symbol names, absolute source roots or iteration
order-dependent names in these reports. Rules are sorted by identity; files are
sorted by relative path. Keep the same input, rules, generator, JDK and dependency
bytes when using `--check`. A changed JDK is a changed provenance record even if
the source output happens to match.

Line numbers stay the same because replacements contain no newlines. Character
columns can move; edit offsets explicitly use Java/JavaScript UTF-16 code units,
not byte offsets. `mapping.json` provides the original source identity for each
readable symbol, so measurements can continue to cite keys such as
`dm.b(IIIIII)V`. Rule evidence and original suffixes make disagreements about
a name reviewable without losing the link to previous profiles.

To adopt another corpus, first establish why its input changed, inspect the exact
definitions and references, update the pinned input digest and review affected
rules. The exported `sourceInventory` and `sourceIdentity` helpers compute that
digest; do not replace it just to bypass a failed check. Re-run focused fixtures,
complete-corpus generation and deterministic `--check` after edits.

## Runtime boundary and next naming work

This is an offline readable source mirror. Existing Deko patches, preparation
profiles, browser entry classes and published artifacts continue to use their
original identities. The generator does not install a runtime renaming adapter.
Literal/reflection names, serialized names, JNI names and external callers are
not remapped by this pass; compilation and binding checks do not establish
whole-game runtime equivalence. Reports keep `runtimeEquivalenceVerified: false`.

Use the readable raster/decoder code to review and explain future changes first.
Expand names by adding evidence-backed exact rules and complete virtual families.
Avoid restructuring methods or changing algorithms in the same naming revision.
If the readable corpus is later made executable in the normal loader, it needs
explicit entry/reflection/native contract handling, reverse identity translation
for profiles/diagnostics, and the existing cold/warm, gameplay and catalog gates.
This naming work makes investigation easier; it is not an FPS improvement claim.
